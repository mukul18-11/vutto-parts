# Vutto Spare Parts System: Specification

## §1 Context and scale
- Vutto buys used two-wheelers, refurbishes them in its own workshops, and sells them through 6 showrooms (5 in Delhi NCR, 1 in Jaipur). It refurbishes ~1,000 bikes a month.
- Two workshops: Delhi NCR (code NCR, ~830 bikes/month, ~32 per working day) and Jaipur (code JPR, ~170 bikes/month, ~6–7 per working day). Workshops work Monday to Saturday (26 days a month) and are closed on Sunday. Each workshop has its own parts store.
- Parts flow: purchase order (PO) → goods receipt (GRN) → putaway → pick → issue to a bike's job card.
- Core idea: Vutto inspects each bike at purchase. The inspection findings become the bike's parts list (job card) before the bike reaches a repair bay, so parts can be reserved or ordered early.
- Out of scope: invoicing, GST accounting, payments, supplier portal, mechanic logins, moving bikes between workshops, stock transfers between workshops.

## §2 Roles and demo logins
- Roles: admin > manager > store_keeper. A higher role can do everything a lower role can, in its own workshop.
- admin: all workshops, catalogue and supplier master data, demo reset, error log. Has no workshop (workshop_id NULL) and picks one with a workshop switcher (?ws=NCR) for workshop-scoped screens.
- manager: own workshop. Creates bikes and inspection findings, confirms/cancels/closes job cards, edits line quantities, reallocates reservations, generates/edits/sends/cancels/short-closes POs, cycle counts, reorder settings.
- store_keeper: own workshop. Receives GRNs, puts away, moves stock, issues parts, records returns, records emergency buys, adds an extra part to a confirmed job card (with a reason).
- Mechanics do not log in. They collect parts at the store counter.
- Five demo logins, all with the same password from env DEMO_PASSWORD, each with a fixed user id (so seeded history shows real names after every reset):
  - admin@demo.example.com (admin) id 00000000-0000-0000-0000-0000000000b0
  - ncr.manager@demo.example.com (manager, NCR) id 00000000-0000-0000-0000-0000000000b1
  - ncr.store@demo.example.com (store_keeper, NCR) id 00000000-0000-0000-0000-0000000000b2
  - jpr.manager@demo.example.com (manager, JPR) id 00000000-0000-0000-0000-0000000000b3
  - jpr.store@demo.example.com (store_keeper, JPR) id 00000000-0000-0000-0000-0000000000b4
- Role and workshop come only from public.profiles, read on every request. Never from JWT user_metadata or app_metadata.

## §3 Data model
All ids are uuid (gen_random_uuid()) unless stated. All tables have created_at timestamptz default now(). Every workshop-scoped table has workshop_id uuid NOT NULL. Enum types are Postgres enums. Actor columns (confirmed_by, received_by, bought_by, user_id, last_reset_by) are plain uuid with no foreign key; names come from a LEFT JOIN to profiles.

### §3.1 Master data
- workshops(id fixed uuid, code text unique 'NCR'|'JPR', name, city). Inserted by migration with fixed uuids. Never truncated.
- profiles(user_id PK → auth.users on delete cascade, full_name, role app_role, workshop_id → workshops null). The app_role enum is declared in ascending order (store_keeper, manager, admin) so private.authorize can compare role >= min_role. CHECK (role = 'admin') = (workshop_id IS NULL).
- suppliers(id, name, city, phone, kind supplier_kind[oem_dealer|wholesaler|local_market], lead_time_days int 0..30, is_active).
- vehicle_models(id, make, model, segment[motorcycle|scooter|moped], unique(make, model)).
- model_variants(id, model_id, name, year_from int, year_to int null (null = still sold), brake_front[drum|disc], brake_rear[drum|disc], start_type[kick|self|kick_self], wheels[spoke|alloy|steel], emission[bs3|bs4|bs6|bs6_obd2|bs6_obd2b], fuel[carb|fi|ei] (ei = Bajaj 'electronic injection' on BS6 Platina/CT)). CHECK year_to IS NULL OR year_to >= year_from.
- parts(id, sku text unique, name (English, ASCII, printed on POs), name_hi text null (Devanagari), aliases text[] (Hinglish/shop slang like 'mobil', 'race wire', 'break shoe'), oem_part_no null, oem_part_no_norm generated = upper(regexp_replace(oem_part_no,'[^A-Za-z0-9]','','g')), category part_category[consumable|wear|model_specific], part_type text (e.g. front_brake_shoe), uom[pcs|set|pair|bottle|kit], standard_price_paise bigint > 0, preferred_supplier_id null, is_universal bool, is_active).
- part_fitments(part_id, variant_id, qty_per_bike int > 0 default 1, source[catalogue|learned], confirmed_count int >= 0 default 0, flagged_count int >= 0 default 0, last_flag_note text null, last_flagged_at timestamptz null, PK(part_id, variant_id)).
- supplier_parts(supplier_id, part_id, supplier_code null, price_paise bigint > 0, PK(supplier_id, part_id)).
- finding_types(id, code unique, label_en, label_hi, area finding_area[engine|brakes|drivetrain|electrical|body|tyres_suspension], is_active).
- finding_type_parts(id, finding_type_id, part_type, qty int > 0, attr_key null, attr_value null). attr_key ∈ {segment (from vehicle_models), brake_front, brake_rear, start_type, wheels, emission, fuel}. A row applies to a bike when attr_key IS NULL or the bike's attribute equals attr_value. A finding resolves to at most one part on any bike (inspection_findings has one job_card_line_id), so a trigger enforces: a finding type has either exactly one row with attr_key NULL, or rows that all use the same attr_key with distinct attr_values. Example: 'front_brake_worn' → (front_brake_shoe, brake_front=drum) and (front_brake_pad, brake_front=disc). A finding that needs two parts is two finding types (e.g. engine_oil_due and oil_filter_due).
- bins(id, workshop_id, code text UNIQUE across all workshops, kind bin_kind[normal|receiving|quarantine], is_active, count_requested_at null). UNIQUE(workshop_id, id). Exactly one receiving and one quarantine bin per workshop (partial unique indexes). Code format: ^(NCR|JPR)-([A-Z][0-9]{2}-[0-9]{2}|RCV|QRN)$, e.g. NCR-A01-03, NCR-RCV, JPR-QRN. The QR label contains exactly the bin code. A BEFORE UPDATE trigger raises VALIDATION if code, kind or workshop_id changes (printed labels and stock rules depend on them), or if is_active becomes false while the bin holds stock.
- reorder_settings(workshop_id, part_id, auto bool, safety_stock int >= 0, max_qty int > 0, preferred_supplier_id null, PK(workshop_id, part_id)). preferred_supplier_id overrides parts.preferred_supplier_id for this workshop (Jaipur buys common parts from a Jaipur supplier).
- doc_counters(workshop_id, doc_type[job_card|po|grn], next_no int, PK(workshop_id, doc_type)). The first migration inserts the 6 rows (NCR and JPR × 3 types) with next_no 1. Codes: JC-NCR-000123, PO-JPR-000045, GRN-NCR-000012, each unique. Incremented with UPDATE ... RETURNING under the workshop lock.
- Master data is never deleted. It is retired with is_active = false. All foreign keys from operational rows to master rows are ON DELETE RESTRICT.

### §3.2 Bikes, inspection, job cards
- bikes(id, workshop_id, reg_no, reg_no_norm generated (uppercase, letters and digits only), model_id NOT NULL, variant_id null, mfg_year int, status bike_status[purchased|at_workshop|in_repair|ready|cancelled], purchased_at, arrived_at null, bay_in_at null, ready_at null, cancelled_at null, cancel_reason null, is_simulated bool default false).
  - CHECK variant (when set) belongs to model_id (enforce in trigger).
  - mfg_year between 1995 and the current IST year, and within [year_from, coalesce(year_to, current IST year)] of the variant when variant is set. Error MFG_YEAR_OUT_OF_RANGE.
  - Timestamps: arrived_at >= purchased_at; bay_in_at >= arrived_at; ready_at >= bay_in_at. Status at_workshop/in_repair/ready requires arrived_at; in_repair/ready requires bay_in_at; ready requires ready_at.
  - Unique reg_no_norm among bikes that are not cancelled.
  - workshop_id never changes after insert.
- inspection_findings(id, workshop_id, bike_id, finding_type_id, qty int null, notes null, job_card_line_id null, no_part_reason null). A finding is resolved when job_card_line_id or no_part_reason is set. Findings are immutable while the bike has a confirmed or closed job card (trigger, error FINDINGS_LOCKED); a cancelled card does not lock them.
- job_cards(id, workshop_id, code unique, bike_id, status job_card_status[draft|confirmed|closed|cancelled], needed_by date null, needs_review_reason text null, confirmed_at, confirmed_by, parts_complete_at null, closed_at, cancelled_at, cancel_reason, is_simulated). Partial unique index: one card per bike WHERE status IN ('draft','confirmed'). confirmed_at/confirmed_by are NULL for draft cards, NOT NULL for confirmed and closed cards, and kept as they were when a card is cancelled. closed_at is set exactly when closed.
- job_card_lines(id, workshop_id, job_card_id, part_id, qty_required int >= 0, qty_reserved int >= 0, qty_issued int >= 0, qty_returned int >= 0, source line_source[suggested|manual|extra], added_reason null, cancelled_at null, cancel_reason null, status generated).
  - Meanings: qty_required = units this bike needs now. qty_reserved = units held on the shelf for this line right now, not yet issued (an issue moves units from qty_reserved to qty_issued). qty_issued = running total issued. qty_returned = running total returned. net_issued = qty_issued - qty_returned. covered = qty_reserved + net_issued. uncovered = qty_required - covered.
  - CHECKs: qty_returned <= qty_issued; covered <= qty_required; cancelled_at IS NULL OR qty_reserved = 0.
  - status is a STORED generated column computed from base columns only: 'cancelled' if cancelled_at is not null; else 'issued' if net_issued >= qty_required; else 'reserved' if covered >= qty_required; else 'partially_reserved' if covered > 0; else 'needed'. No code writes it.
  - Partial unique index on (job_card_id, part_id) WHERE cancelled_at IS NULL: one live line per part per card. Adding the same part again increases qty_required.
  - part_id cannot change once the card is confirmed.
  - Only lines on confirmed cards may hold reservations (trigger).

### §3.3 Purchasing
- purchase_orders(id, workshop_id, code unique, supplier_id, status po_status[draft|sent|partially_received|received|closed|cancelled], sent_at null, expected_on date null (IST calendar date), cancel_reason null, is_simulated). Partial unique: one draft per (workshop_id, supplier_id).
- po_lines(id, workshop_id, po_id, part_id, qty_ordered int > 0, qty_accepted int >= 0, qty_rejected int >= 0, qty_cancelled int >= 0, unit_price_paise bigint null (> 0 when set; incl. GST), source[suggested|manual], open_qty generated = qty_ordered - qty_accepted - qty_cancelled). CHECK qty_accepted + qty_cancelled <= qty_ordered. UNIQUE(po_id, part_id). There is NO link from a PO line to a job card line: supply is per (workshop, part).
- grns(id, workshop_id, code unique, po_id, supplier_id, supplier_invoice_no, invoice_no_norm, invoice_date date, received_by, received_at, is_simulated).
- grn_lines(id, workshop_id, grn_id, po_line_id, part_id, qty_received int > 0, qty_accepted int >= 0, qty_damaged int >= 0, qty_wrong_part int >= 0, unit_price_paise bigint > 0). CHECK qty_received = qty_accepted + qty_damaged + qty_wrong_part. UNIQUE(grn_id, po_line_id).
- Damaged and wrong-part units at GRN are handed back to the delivery person. They never enter stock and create no stock move. They are recorded on the GRN line and po_lines.qty_rejected, and stay owed (open_qty) until short-closed.

### §3.4 Stock
- stock_balances(workshop_id, bin_id, part_id, on_hand int >= 0, PK(bin_id, part_id)). Composite FK (workshop_id, bin_id) → bins(workshop_id, id). Rows that reach 0 are kept. Written ONLY by the stock_moves AFTER INSERT trigger (insert ... on conflict do update for the destination; for the source, update ... where on_hand >= qty and raise INSUFFICIENT_BIN_STOCK if no row was updated). The demo reset's rebuild in §15 and the TRUNCATE in reset_demo and test_clear are the only exceptions.
- stock_moves(id bigint generated always as identity, workshop_id, part_id, move_type, qty int > 0, from_bin_id null, to_bin_id null, job_card_line_id null, grn_line_id null, emergency_buy_id null, reason text null, note text null, user_id null, request_id uuid null, is_simulated bool, created_at). Return moves store reason = the return reason code (not_needed|issued_by_mistake|damaged|wrong_fitment) and the note. Append-only: a trigger blocks UPDATE and DELETE for every role. Composite FKs for both bins. History is ordered by id.
- Move types and allowed bins (enforce in the trigger; from → to):
  - grn: none → receiving (accepted GRN units). Needs grn_line_id.
  - putaway: receiving → normal.
  - move: normal|receiving → normal; normal|receiving → quarantine (reason required); quarantine → normal (manager, reason required).
  - issue: normal|receiving → none. Needs job_card_line_id.
  - return_to_stock: none → normal. Needs job_card_line_id.
  - return_to_quarantine: none → quarantine. Needs job_card_line_id.
  - return_to_supplier: quarantine → none. Reason required.
  - adjust_in: none → normal|receiving|quarantine. Reason required.
  - adjust_out: normal|receiving|quarantine → none. Reason required.
  - emergency_in: none → receiving. Needs emergency_buy_id.
  - CHECK: from and to are not both null, and differ.
- emergency_buys(id, workshop_id, job_card_line_id, part_id, vendor_name, qty int 1..50, unit_price_paise bigint > 0, reference_price_paise bigint null, qty_issued int, qty_to_stock int, reason emergency_reason[no_stock|supplier_late|wrong_part_received|other], note null, bill_photo_path null, bought_by, is_simulated). CHECK qty = qty_issued + qty_to_stock.

### §3.5 System tables
- idempotency(user_id, request_id uuid, fn text, payload_hash text, result jsonb null, created_at, PK(user_id, request_id)). RLS on, no policies: clients cannot read it.
- activity_log(id bigint identity, workshop_id null, entity_type text, entity_id uuid, action text, summary jsonb, user_id null, request_id null, is_simulated, created_at). Append-only (same trigger as stock_moves). Every mutating RPC writes exactly one row.
- app_errors(id bigint identity, created_at, user_id, route, code, message, request_id). Written through RPC log_app_error; admin can read.
- demo_meta(id int PK check id = 1, anchor_date date, last_reset_at timestamptz, last_reset_by uuid null, cooldown_seconds int default 120). The migration that creates it inserts its single row (id 1; the other columns null or default); apply_seed updates it.

## §4 Stock definitions (one definition each, used everywhere)
For a (workshop w, part p):
- usable_on_hand = sum(on_hand) over w's bins of kind normal or receiving. Quarantine never counts.
- quarantine_on_hand = sum(on_hand) in w's quarantine bin. Shown separately.
- reserved = sum(qty_reserved) over w's job card lines.
- available = usable_on_hand - reserved.
- on_order = sum(open_qty) over po_lines of w's POs with status draft, sent or partially_received (overdue POs still count).
- outstanding_demand = sum(qty_required - net_issued) over non-cancelled lines on w's confirmed cards.
- shortfall = sum(uncovered) over non-cancelled lines on w's confirmed cards.
- One SQL view, public.v_stock_position (security_invoker), returns all of these per (workshop, part). Its keys are workshops CROSS JOIN parts WHERE (select private.is_admin()) OR workshop id = (select private.my_workshop_id()) (master data is readable by everyone, so without this filter a Jaipur user would see NCR rows with zeros). Each measure comes from its own CTE aggregated GROUP BY workshop_id, part_id, LEFT JOINed to the keys with coalesce(…, 0). Never join two sources (balances, lines, PO lines) before aggregating; that multiplies the sums. No TypeScript code computes stock numbers.
- Invariants that hold after every committed RPC (private.check_invariants() returns the violating rows; it must return none):
  1. stock_balances.on_hand = sum of qty moved in − sum moved out, per (bin, part), from stock_moves.
  2. on_hand >= 0 everywhere.
  3. 0 <= reserved <= usable_on_hand per (w, p).
  4. If available > 0 then shortfall = 0 per (w, p) (free stock never sits while a confirmed bike waits).
  5. Lines on cards that are not confirmed hold qty_reserved = 0.
  6. Each line's qty_issued / qty_returned equal the sums of its issue / return moves.
  7. po_lines.qty_accepted = sum(grn_lines.qty_accepted) for that PO line; qty_rejected = sum(damaged + wrong).
  8. For each emergency buy, emergency_in qty = qty_issued + qty_to_stock.
  9. For confirmed cards, parts_complete_at is non-null exactly when every non-cancelled line has uncovered = 0 and needs_review_reason is null. Draft and cancelled cards: null. Closed cards: non-null.

## §5 Bike and job card lifecycle
### §5.1 Bike statuses (BEFORE UPDATE trigger; anything else raises INVALID_TRANSITION; RPCs set timestamps with now(), never from the client, and an UPDATE never overwrites a set timestamp. The rules are enforced on UPDATE only, so rows INSERTed as postgres (test fixtures, the seed copy) may carry explicit past timestamps)
- purchased → at_workshop (mark_arrived: sets arrived_at)
- at_workshop → in_repair (start_repair: sets bay_in_at; requires a confirmed job card)
- in_repair → ready (only inside close_job_card: sets ready_at)
- purchased | at_workshop | in_repair → cancelled (only inside cancel_bike)
### §5.2 Job card rules
- create_bike creates the bike, its findings, and a draft job card with suggested lines (§9) in one transaction.
- While the card is draft: findings can be edited (suggested lines are regenerated; manual lines are kept); lines can be switched to another part (becomes manual); no reservations.
- confirm_job_card: allowed when the bike is purchased, at_workshop or in_repair. Refuses with UNRESOLVED_FINDINGS (listing them) while any finding is unresolved. Sets needed_by if null: IST date of arrived_at if arrived, else IST date of purchased_at + 2 days. Sets confirmed_at/by. Runs allocation for every part on the card. A card with no live lines is complete immediately.
- set_needed_by(card, date): manager. Affects only future allocations; never takes reservations away.
- add_job_card_line(card, part, qty, reason): confirmed cards. Manager (source manual) or store keeper (source extra, reason required, e.g. mechanic found a broken clutch cable). If the part is already on the card, qty_required increases. Allocates immediately. When a manager adds a line to a card with needs_review_reason set, needs_review_reason is cleared in the same call (activity_log keeps the old value); a store keeper's extra line does not clear it. Draft cards get parts only through findings (resolve_finding, switch_line_part).
- set_line_qty(line, new_qty, reason): manager. new_qty >= net_issued or RETURN_PARTS_FIRST. A decrease releases the excess reservation and runs allocate_free_stock(w, p). An increase runs allocate_free_stock(w, p, line). new_qty = 0 with net_issued = 0 cancels the line.
- reallocate_reservation(from_line, to_line, qty, reason): manager. Same workshop and part, both cards confirmed, qty <= from_line.qty_reserved and <= to_line.uncovered (else VALIDATION). Issued units can never be reallocated.
- cancel_job_card(card, reason): manager. Refuses with ISSUED_PARTS_OUTSTANDING (listing lines) while any line has net_issued > 0. Otherwise releases all reservations (re-allocated FIFO to other bikes), cancels all lines, sets status cancelled and parts_complete_at = null. POs are never changed automatically; excess supply shows in "Excess on order".
- close_job_card(card, drop_remaining bool, reason): manager. Bike must be in_repair. Without drop_remaining, every live line must have qty_reserved = 0 and net_issued = qty_required, else OPEN_LINES (listing them). If needs_review_reason is set, refuse with OPEN_LINES unless drop_remaining is true (which clears it). With drop_remaining (reason required): release reservations, set qty_required = net_issued, cancel lines left at 0. Then: learned fitment update (§9.3); if parts_complete_at is still null, set it to now() (so a closed bike is never counted as still waiting); closed_at; bike → ready.
- create_job_card(p_request_id, p_bike_id): manager. BIKE_NOT_ACTIVE if the bike is ready or cancelled. If the bike already has a draft or confirmed card, return it unchanged. Otherwise create a draft card (next_code), regenerate suggested lines from the bike's existing findings per §9.1 and relink each finding's job_card_line_id to the new lines (no_part_reason kept). This is how a bike gets a new card after its card was cancelled.
- cancel_bike(bike, reason): manager. Not for ready bikes. Runs cancel_job_card on the open card (so it fails if parts are issued), then sets the bike cancelled.
- parts_complete_at is maintained by private.refresh_card_completeness(card_id), called at the end of every RPC that changes a confirmed card's lines, reservations or needs_review_reason: set to now() when the card becomes complete (and it was null); set to null when it stops being complete.

## §6 Allocation (reservations)
- private.allocate_free_stock(w, p, priority_line_id default null): while available(w,p) > 0, reserve to the priority line first (if it has uncovered need), then to non-cancelled lines on w's confirmed cards with uncovered > 0, in FIFO order: job_cards.needed_by ASC NULLS LAST, job_cards.confirmed_at ASC, job_card_lines.id ASC. Fill each line fully before the next. Never takes an existing reservation away.
- Every RPC that can increase available stock, or a confirmed line's uncovered qty, calls it for each part it touched, at the end: GRN, adjust_in, every return reason (including wrong_fitment), cancellations, set_line_qty (both directions), add_job_card_line, close with drop, move from quarantine, emergency buys.
- allocate_free_stock and dereserve_excess call refresh_card_completeness for every card whose reservations they change.
- private.dereserve_excess(w, p): if reserved > usable_on_hand (after adjust_out, move to quarantine, return_to_supplier), release the excess in reverse FIFO order (latest needed_by first, nulls first; then latest confirmed_at; then highest line id), set those cards incomplete, and return their card codes so the UI can show "these bikes lost their reservation".
- Only reallocate_reservation (manager) moves a reservation from one bike to another.

## §7 Purchasing
### §7.1 Draft PO generation: generate_draft_pos(workshop) (manager)
Runs under the workshop lock, in one transaction, and is idempotent (running it twice with no other change gives identical results):
1. Compute the target set of suggested lines (steps 2–5) without deleting anything first.
2. For each active part with demand or reorder settings, compute projected = usable_on_hand + on_order − outstanding_demand (on_order now includes only manual draft lines plus sent/partially received open_qty).
3. Requirement:
   - Auto parts (reorder_settings row with auto = true; consumables and common wear parts): ROP = ceil(avg_daily_issue_28d × lead_time_days) + safety_stock. If projected <= ROP, order max(max_qty, ROP + 1) − projected.
   - On-demand parts (everything else, including all model_specific parts): order max(0, −projected).
   - avg_daily_issue_28d = max(0, issued qty − qty returned from job cards) over the 28 complete IST days ending yesterday, as numeric, divided by 28. Never integer division. Only issue and return moves count as demand (an emergency buy counts once, through its issue move); putaway, moves and adjustments never do. Today's issues change the ROP from tomorrow; the UI says "based on 28 days to <yesterday>".
   - If the workshop has fewer than 7 complete days of issue history, auto parts use ROP = safety_stock and the UI says "Not enough history".
   - Never create a PO line with qty <= 0.
4. Effective supplier = reorder_settings.preferred_supplier_id ?? parts.preferred_supplier_id. If none: no line; return the part in `unsourced` ("Needs supplier").
5. Skip parts that already have a manual line on that supplier's draft. Otherwise upsert by (po_id, part_id) on the single draft PO for (w, supplier), creating the PO (with a code) if needed: insert if missing (added); update qty/price only when different (changed); leave equal lines untouched. Price = supplier_parts price ?? last GRN price ?? standard_price_paise.
6. Delete suggested lines on w's drafts that are not in the target set (removed), then delete drafts left with no lines. Return {added, changed, removed, unsourced[]}.
### §7.2 Draft edits (manager): add_draft_line(p_request_id, p_workshop_id, p_supplier_id, p_part_id, p_qty, p_unit_price_paise default null) creates the draft PO for (workshop, supplier) with a code if none exists, and raises VALIDATION if the part already has a line on it; update_draft_line(p_request_id, p_line_id, p_qty, p_unit_price_paise); remove_draft_line(p_request_id, p_line_id). Any edit makes the line manual; regeneration never touches manual lines. A removed suggested line comes back on the next regeneration if the demand still exists.
### §7.3 send_po(po) (manager)
Requires status draft, at least one line, every qty > 0 and every price set. Sets status sent, sent_at = now(), expected_on = ist_date(sent_at) + supplier.lead_time_days. Returns a plain-text message for WhatsApp listing for each line: SKU, part name, OEM part no (if any), supplier code (if any), qty with uom, unit price incl. GST; for model_specific parts also a fitment line, e.g. "Fits: Hero Splendor Plus BS6 Self Alloy i3S 2020–2023, drum, kick_self". After sending, lines, quantities, prices and supplier are immutable (VALIDATION); only expected_on can change (set_po_expected_on, date >= IST today). The date math lives in private.expected_on(p_sent_at timestamptz, p_lead int) so it can be tested with explicit times.
### §7.4 receive_grn (store_keeper)
Input: po_id, supplier_invoice_no (1–40 chars, required), invoice_date (not after IST today), allow_duplicate_invoice bool, lines[{po_line_id, qty_received, qty_damaged, qty_wrong_part, unit_price_paise}].
- PO status must be sent or partially_received. Each po_line belongs to the PO; no repeats; input lines with qty_received = 0 are ignored (no grn_line row); qty_received > 0 on at least one line; qty_accepted = qty_received − damaged − wrong is computed by the server.
- accepted <= open_qty per line, else OVER_RECEIPT with detail {part, ordered, accepted_so_far, max_now}. The whole GRN is rejected; no partial posting.
- invoice_no_norm = upper(letters and digits only). If the same supplier already has a GRN with the same invoice_no_norm and an invoice_date in the same Indian financial year (April–March), raise DUPLICATE_INVOICE (detail: GRN code, who, when) unless allow_duplicate_invoice is true (the UI asks "Does this invoice cover both deliveries?").
- Accepted units: one grn move per line into w's receiving bin. Update po_lines.qty_accepted/qty_rejected. refresh_po_status. allocate_free_stock for every part. Return the allocation result: which bikes (reg no, card code) just got which parts, so the store keeper sees "2 reserved for DL3SAB1234, waiting 3 days: issue now".
- Prices: the GRN line price is prefilled from the PO and may differ (invoice price wins). A difference >= 5% shows as a price variance; it never blocks. Last purchase price for a part = latest grn_line.unit_price_paise among lines with qty_accepted > 0 (view v_part_last_price). Emergency buys never affect it.
### §7.5 Short-close and cancel (manager)
- short_close_po(po, line_ids or null for all, reason): status sent or partially_received; sets qty_cancelled = qty_ordered − qty_accepted on chosen lines with open_qty > 0.
- cancel_po(po, reason): draft → delete it and its lines. Sent with nothing accepted → all lines qty_cancelled = qty_ordered, status cancelled. Anything accepted → refuse with ALREADY_RECEIVED ("use short-close").
- private.refresh_po_status(po): the only writer of status for non-draft POs. With A = sum(qty_accepted), O = sum(open_qty): O = 0 and A = 0 → cancelled; O = 0 and every line accepted = ordered → received; O = 0 otherwise → closed; O > 0 and A > 0 → partially_received; O > 0 and A = 0 → sent.
### §7.6 ETA for waiting bikes (pegging view v_line_eta)
Rank w's uncovered lines for part p by the FIFO key with a running total of uncovered qty. Rank open PO lines for (w, p) on sent/partially_received POs by expected_on, then PO code, with a running total of open_qty. A line's ETA is the expected_on of the first PO whose running total covers the line's running total. Otherwise "In draft PO-…" if a draft covers it, else "Not ordered". Overdue = expected_on < IST today.
### §7.7 Excess on order: per (w, p), excess = max(0, least(on_order, projected − target)), where target = max(max_qty, ROP + 1) for auto parts (the level §7.1 orders up to, so a PO that generation just suggested is never shown as excess) and 0 for on-demand parts. Listed for managers so they can short-close.

## §8 Issue, returns, emergency buys
### §8.1 issue_to_job_card(line_id, bin_id, qty) (store_keeper)
- Card confirmed (JOB_CARD_NOT_CONFIRMED); line not cancelled (LINE_CANCELLED); bike at_workshop or in_repair (BIKE_NOT_ARRIVED); bin in the card's workshop (NOT_FOUND) and of kind normal or receiving (BIN_NOT_ISSUABLE).
- Run allocate_free_stock(w, p, line) first. Then qty <= line.qty_reserved (else INSUFFICIENT_RESERVATION with detail {reserved, available, held_by: [card codes holding this part]}), and qty <= bin on_hand (else INSUFFICIENT_BIN_STOCK with detail listing bins that hold the part).
- Effect: issue move; qty_reserved −= qty; qty_issued += qty. Always issues line.part_id (no part parameter). One bin per call; the UI makes two calls for two bins.
### §8.2 return_from_job_card(line_id, qty, reason, to_bin_id null, note null) (store_keeper)
Card must be confirmed (returns after close: manager uses adjust_in). qty <= net_issued (RETURN_EXCEEDS_ISSUED). Reasons:
- not_needed: return_to_stock into to_bin (normal); qty_required −= qty; allocate.
- issued_by_mistake: return_to_stock into to_bin (normal); qty_required unchanged (need reopens); allocate with priority to this line.
- damaged: return_to_quarantine into w's quarantine bin (to_bin ignored); qty_required unchanged; allocate with priority to this line.
- wrong_fitment: return_to_stock into to_bin (normal); then qty_required = net_issued and qty_reserved = 0 on this line (the part does not fit, so its remaining need and any reservation are dropped; the manager adds the correct part); note required (>= 5 chars); flagged_count + 1, last_flag_note = note, last_flagged_at = now() on (part, bike variant) (upsert a learned row if none; skip if variant unknown); set job_cards.needs_review_reason = 'wrong_fitment: <part>' so the bike shows "Choose correct part" on the blocked board until a manager adds a line or clears it (clear_needs_review); allocate (FIFO).
- Lines left with qty_required = 0 and net_issued = 0 get cancelled_at.
### §8.3 record_emergency_buy(line_id, qty, unit_price_paise, vendor_name, reason, note, bill_photo_path null) (store_keeper)
- The buy is always recorded, because the money is already spent. Only NOT_AUTHENTICATED, NO_PROFILE, FORBIDDEN, NOT_FOUND, VALIDATION and BILL_NOT_FOUND refuse it. If the card is not confirmed, the line is cancelled, or the bike is not at_workshop/in_repair, the buy is recorded with n = 0 (all units go to stock) and the result carries {issued: 0, warning: 'JOB_CARD_NOT_CONFIRMED'|'LINE_CANCELLED'|'BIKE_NOT_ARRIVED'}.
- reference_price_paise = snapshot of: effective supplier's supplier_parts price ?? last GRN price ?? standard_price_paise.
- Moves: emergency_in of qty into receiving. Then, if n = min(qty, qty_required − net_issued) > 0, one issue move of n from receiving with job_card_line_id and emergency_buy_id set. Then in ONE UPDATE of the line (so the covered <= qty_required CHECK never sees a half state): qty_issued = qty_issued + n, qty_reserved = least(qty_reserved, qty_required − (net_issued + n)). Unlike §8.1, this issue does not consume the line's reservation; any reservation no longer needed is released. emergency_buys.qty_issued = n; qty_to_stock = qty − n (stays free in receiving). Allocate.
- premium = (unit_price − reference) / reference, computed in views as numeric, null if reference is null or 0.
- bill_photo_path, when given, must match ^<workshop_id>/<uuid>\.(jpg|png|webp)$ and exist in storage.objects for bucket 'bills' (BILL_NOT_FOUND). attach_emergency_bill(buy_id, path) sets it later, only while it is null.
### §8.4 Moves and counts
- move_stock(part, from_bin, to_bin, qty, reason null) (store_keeper; quarantine → normal needs manager): bins in the same workshop; rules per §3.4. Moving into quarantine runs dereserve_excess. Moving out of quarantine runs allocate.
- adjust_stock(bin, part, counted_qty 0..9999, expected_on_hand, reason[count_correction|lost|found]) (manager): if current on_hand ≠ expected_on_hand raise STALE_COUNT (someone moved stock since the count screen loaded). delta = counted − current; post adjust_in/adjust_out or nothing. Then dereserve_excess or allocate. Return released card codes.
- return_to_supplier(p_request_id, p_bin_id, p_part_id, p_qty, p_reason) (manager): p_bin_id must be the workshop's quarantine bin (else BIN_KIND_NOT_ALLOWED); the workshop comes from the bin.
- request_bin_count(bin) (store_keeper): sets count_requested_at; the bin appears on the manager's count list. Any adjust_stock call on that bin, including a no-op count, clears it.

## §9 Fitment and suggestions
### §9.1 Candidate parts for a finding on a bike
1. The applicable finding_type_parts row (at most one, §3.1): attr_key null, or the bike's attribute matches. Unknown variant → only rows with attr_key null or attr_key = segment (segment comes from the model, which is always known).
2. For that part_type: candidates = active parts with that part_type and a fitment to the bike's variant that is either source catalogue or learned with confirmed_count >= 1. Exclude from auto-pick any fitment with flagged_count >= max(1, confirmed_count), the same rule that makes the §9.2 badge red (still selectable by hand with the red warning).
3. If no variant-specific candidate exists (or the variant is unknown), use active is_universal parts of that part_type.
4. Auto-pick order: catalogue before learned, then (confirmed_count − flagged_count) desc, then standard_price_paise asc, then sku asc. The UI shows "1 of N options" with a switch, using the read functions public.finding_candidates(p_finding_id) and public.line_candidates(p_line_id) (SECURITY INVOKER), which return this ranked list.
5. qty = finding.qty if set, else fitment.qty_per_bike, else finding_type_parts.qty.
6. Findings that resolve to the same part merge into one line; all those findings link to that line. qty = the sum, over distinct finding types, of the largest qty among that type's findings (two 'rear_brake_worn' findings do not double the shoes, but two different finding types that need the same part add up).
7. No candidate → the finding stays unresolved. The manager picks a part (search filtered to the part_type, with "show all"), or marks "No part needed" with a reason.
### §9.2 Fit badge at issue time (UI only; the server never blocks on fitment)
Read through public.fit_badge(p_line_id) (SECURITY INVOKER) → {badge, confirmed_count, flagged_count, last_flag_note}, called before the Issue tap. Checked in this order: Red when a fitment row for the variant has flagged_count >= max(1, confirmed_count), even for a universal part (second tap; shows last_flag_note). Else Amber "Not confirmed for <model variant year>, check on bike" when there is no fitment row and the part is not universal, or 0 < flagged_count < confirmed_count (second tap). Else Green "Fits (confirmed N)" (or "Universal"). Unknown variant: Amber unless universal.
### §9.3 Learning
- At close_job_card: for each line with net_issued > 0, bike variant known, part not universal: upsert part_fitments(part, variant) with confirmed_count + 1 (insert as source learned if no row).
- At a wrong_fitment return: flagged_count + 1 (§8.2).
- Idempotency guarantees retries never double count.

## §10 Reports and metric definitions (all in SQL; security_invoker views or SECURITY INVOKER functions with p_as_of date default private.ist_today())
- Part-wait (north star): for each arrived bike with a confirmed card (not cancelled), start = greatest(arrived_at, confirmed_at); end = coalesce(parts_complete_at, closed_at), or p_as_of for bikes still waiting; wait = max(0, end − start). Bikes whose parts were reserved before arrival have wait 0. A bike belongs to the period in which its wait started. Report: n, % with zero wait, median and p90 wait in hours over all n (still-waiting bikes included with their wait so far, labelled "includes N still waiting", so blocked bikes can never make the median look better). When n < 5 show "–" and "n=3, too few". Combined (admin, all workshops) metrics pool the underlying rows; never average two workshop figures.
- Blocked bikes board (v_blocked_bikes): confirmed cards, bike at_workshop or in_repair, parts_complete_at null; oldest start first; for each: reg no, model/variant/year, waiting since, missing parts with qty and ETA (§7.6), needs_review_reason, and a "reallocation candidate" marker on lines whose reservation sits on a bike that is itself blocked on another part. Separate list "Inbound shortfalls": purchased (in transit) bikes with uncovered lines.
- Emergency share = emergency spend / (emergency spend + GRN accepted value) in the range (GRN value = qty_accepted × GRN unit price; damaged units excluded). Show the ₹ numerator and denominator next to the %. Premium % is weighted: sum(qty × (price − reference)) / sum(qty × reference) over buys with a reference price (negative premiums kept); buys without one are counted separately.
- Dead stock (dead_stock(w, as_of, days=90)): (w, p) where available > 0 AND no issue move in the last 90 IST days AND no grn or emergency_in move in the last 90 IST days. dead_qty = available (reserved units are never dead). Value = dead_qty × last price (v_part_last_price, falling back to supplier price, then standard price). putaway, move, adjust and return moves never reset the age. Quarantine stock is listed separately as "Pending return to supplier".
- Tile totals are summed in paise in SQL and rounded once at display; every tile links to its list and the list footer shows the same SQL total.
- Wrong-fit rate = sum(qty) of return_to_stock moves with reason 'wrong_fitment' / sum(qty) of issue moves in the range.
- Reorder suggestions use §7.1 exactly (same SQL function as generation).
- Ratios use nullif(denominator, 0) and show "–" when null. Aggregates are never computed in TypeScript (PostgREST returns at most 1,000 rows).

## §11 RPC contract
### §11.1 Shape
- Public RPCs live in schema public with SECURITY DEFINER, SET search_path = public, pg_temp, and all private.* and extensions.* references fully qualified. Unchecked helpers live in schema private (not exposed by the Data API).
- Every mutating RPC takes p_request_id uuid as its first parameter, returns jsonb, and does in this order:
  1. private.begin_request(fn, p_request_id, payload): first PERFORM pg_advisory_xact_lock_shared(hashtextextended('demo:gate', 0)) (so a demo reset can never deadlock with a running RPC, §15) and raise NOT_AUTHENTICATED if auth.uid() is null; then INSERT into idempotency (user_id = auth.uid()) ON CONFLICT DO NOTHING. If the row already exists with the same fn and payload_hash: return its stored result immediately (and do nothing else). Different fn or payload: raise IDEMPOTENCY_KEY_REUSED. A concurrent duplicate waits on the primary key until the first commits.
  2. Load the target row (line, card, PO, bin) and get its workshop_id. Never trust a workshop_id parameter, except for root-creating RPCs (create_bike, generate_draft_pos, add_draft_line), where a non-admin may pass null (= own workshop) or their own id and admin must pass one (WORKSHOP_REQUIRED).
  3. private.authorize(min_role, workshop_id): raises NOT_AUTHENTICATED (auth.uid() null), NO_PROFILE, FORBIDDEN (role too low), or NOT_FOUND (workshop differs; same error as a missing id). Admin passes any workshop. Workshops are compared with IS DISTINCT FROM.
  4. private.lock_workshop(workshop_id): pg_advisory_xact_lock(hashtextextended('ws:' || id, 0)). All stock and reservation changes in a workshop are serialised; this removes deadlocks and lost updates. Re-read rows after the lock.
  5. Do the work. Write one activity_log row. user ids always come from auth.uid(); no RPC has a user parameter.
  6. Assert private.check_invariants_for(w, parts touched) and raise INVARIANT_VIOLATION if it returns rows.
  7. private.finish_request(...) stores the result in the idempotency row. A failed call rolls back and stores nothing.
- Declare each RPC with SET lock_timeout = '3s'. Use only transaction-level advisory locks.
- Client rule: the request_id is created once when a form mounts (uuid v4 from the 'uuid' package), reused for every retry and double tap, and replaced only after a confirmed success.
- Exempt from steps 1–7: log_app_error (no idempotency row, lock, activity_log or invariant check; its p_ref_request_id is stored only in app_errors.request_id), public.reset_demo() (no request_id; the try-lock and cooldown stop double submits) and public.reseed_if_stale_service() (service_role only, see §11.2).
- Read RPCs and views are SECURITY INVOKER so RLS applies. Never switch a read function to SECURITY DEFINER to work around a missing grant. The one exception is public.health() (§16): SECURITY DEFINER with search_path set, returning only {ok, schema_version}, because anon has no access to schema supabase_migrations.
### §11.2 Grants
- First migration, after creating the extensions, runs exactly: ALTER DEFAULT PRIVILEGES FOR ROLE postgres REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC; ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public REVOKE ALL ON TABLES FROM anon, authenticated; ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public REVOKE ALL ON SEQUENCES FROM anon, authenticated; ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public REVOKE ALL ON FUNCTIONS FROM anon, authenticated; REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA public FROM PUBLIC, anon, authenticated; REVOKE CREATE ON SCHEMA public FROM PUBLIC. (Postgres grants EXECUTE on new functions to PUBLIC by default; revoking only from anon and authenticated does not remove that.)
- So every migration that creates or re-creates a function ends with explicit grants: REVOKE EXECUTE ON FUNCTION … FROM PUBLIC, anon; GRANT EXECUTE … TO authenticated (public RPCs and the read functions). Every new view or table gets GRANT SELECT … TO authenticated.
- authenticated: SELECT on tables/views (RLS filters rows); INSERT/UPDATE only on master data tables (suppliers, vehicle_models, model_variants, parts, part_fitments, supplier_parts, finding_types, finding_type_parts, bins, reorder_settings) behind RLS policies allowing admin only (reorder_settings: manager of that workshop or admin). No DELETE or TRUNCATE on anything.
- EXECUTE on public RPCs: authenticated only. anon may execute only public.health(). public.reseed_if_stale_service(): service_role only. private schema: USAGE for authenticated, and EXECUTE only on private.my_role(), private.my_workshop_id(), private.is_admin(), private.ist_date(), private.ist_today(), private.po_requirements() and private.parts_search_text() (needed inside SECURITY INVOKER read functions and the parts search index expression); no other private function is executable by clients.
### §11.3 RLS
- RLS enabled on every table. Workshop-scoped SELECT policy: (select private.is_admin()) OR workshop_id = (select private.my_workshop_id()). Master data without a workshop_id: any authenticated user can read. bins and reorder_settings have a workshop_id and use the workshop-scoped SELECT policy (a Jaipur user sees no NCR bins). profiles: own row, same-workshop rows, admin rows (so names show), or all for admin. workshops and demo_meta: any authenticated user can read. app_errors: admin reads. activity_log rows with workshop_id null: admin only. idempotency and doc_counters: no policies. Master data writes: admin only; reorder_settings also by that workshop's manager (WITH CHECK is_admin() or (workshop_id = my_workshop_id() and my_role() = 'manager')).
- Every public view is created WITH (security_invoker = true). No materialized views in public. Nothing in public references auth.users (names come from profiles.full_name).
### §11.4 Errors
RAISE EXCEPTION USING ERRCODE = 'P0001', MESSAGE = '<CODE>', DETAIL = '<json>'. Codes (one TS const in src/lib/errors.ts with en and hi text): NOT_AUTHENTICATED, NO_PROFILE, FORBIDDEN, NOT_FOUND, WORKSHOP_REQUIRED, VALIDATION, IDEMPOTENCY_KEY_REUSED, INVARIANT_VIOLATION, INVALID_TRANSITION, MFG_YEAR_OUT_OF_RANGE, FINDINGS_LOCKED, UNRESOLVED_FINDINGS, JOB_CARD_NOT_CONFIRMED, LINE_CANCELLED, BIKE_NOT_ARRIVED, BIKE_NOT_ACTIVE, OPEN_LINES, ISSUED_PARTS_OUTSTANDING, RETURN_PARTS_FIRST, INSUFFICIENT_RESERVATION, INSUFFICIENT_BIN_STOCK, BIN_NOT_ISSUABLE, BIN_KIND_NOT_ALLOWED, RETURN_EXCEEDS_ISSUED, STALE_COUNT, OVER_RECEIPT, DUPLICATE_INVOICE, PO_NOT_SENDABLE, PO_NOT_RECEIVABLE, ALREADY_RECEIVED, BILL_NOT_FOUND, RESET_IN_PROGRESS, RESET_COOLDOWN, DEMO_TEMPLATE_STALE, SESSION_EXPIRED, SESSION_CHANGED. Unknown errors show "Something went wrong (ref XXXX)" and are logged via log_app_error.

## §13 Time and money

GST (labelled on screens).

## §15 Seed and demo reset
- scripts/seed/generate.ts is a pure, deterministic function: one mulberry32 PRNG with a constant seed, deterministic uuids (UUIDv5), no Date, Math.random or Intl. All times are integer day/minute offsets from a template day T0. It writes supabase/seed/template.sql, which starts with DROP SCHEMA IF EXISTS demo_seed CASCADE; CREATE SCHEMA demo_seed; then CREATE TABLE demo_seed.<t> (LIKE public.<t> INCLUDING DEFAULTS) per table (no generated or identity columns), then multi-row INSERTs of up to 1,000 rows (never COPY … FROM stdin, which neither the CLI seeder nor node-postgres can run) — catalogue, suppliers, bins, settings, and ~90 days of simulated operations. Actor columns use only the fixed demo user ids from §2. activity_log rows are written only for planted entities (row budget).
- public.reset_demo() (admin only): pg_try_advisory_xact_lock on a reset key (else RESET_IN_PROGRESS); cooldown from demo_meta (else RESET_COOLDOWN); pg_advisory_xact_lock(hashtextextended('demo:gate', 0)) (waits for running RPCs, which hold it shared, and makes new ones queue behind it); lock all workshops in id order; TRUNCATE the explicit list from private.reset_tables() (operational and catalogue tables; never workshops, profiles, auth.*, demo_meta, demo_seed.*) with RESTART IDENTITY and without CASCADE; copy every demo_seed table into public in FK order, shifting every date and timestamptz column by (p_anchor − demo_seed.meta.anchor_date) days, where p_anchor is apply_seed's argument (private.ist_today() for a reset). template.sql also creates the one-row table demo_seed.meta(anchor_date) holding the template's own anchor (T0 + 90); apply_seed reads it, never copies it to public, and then sets demo_meta.anchor_date = p_anchor. Column lists come from information_schema.columns of the public table, excluding generated columns and identity columns (stock_moves.id, activity_log.id, app_errors.id), intersected with the demo_seed columns. If a demo_seed table is missing, or a public NOT NULL column without a default is missing from demo_seed, raise DEMO_TEMPLATE_STALE ("run pnpm seed:gen and reload the template"). Identity tables are inserted ORDER BY the seed row's id so history order is kept and the sequence continues past the last row. Before copying, ALTER TABLE … DISABLE TRIGGER USER on every copied table (FK constraint triggers stay on); after copying, ENABLE TRIGGER USER. Then rebuild stock_balances from stock_moves with one INSERT … SELECT … GROUP BY; set doc_counters to max seeded number + 1; truncate idempotency; update demo_meta; run check_invariants and the planted-scenario checks and RAISE (rolling back) on failure. Must finish in under 3 seconds locally. reset_demo and reseed_if_stale_service are declared with SET statement_timeout = '30s' and SET lock_timeout = '10s'. Supabase limits the authenticated role to 8 s, and PostgREST applies a function's own statement_timeout before the call (hoisted transaction settings), so the reset gets 30 s through the app. In the SQL editor and pg-based tests, run SET statement_timeout = '30s' before calling apply_seed. A page that loads during a reset may render empty once; the "Demo data reset at …" banner explains it.
- No seeded event is in the future: events exist only on days anchor−180 .. anchor−1, between 09:30 and 19:00 IST. Today is empty so the reviewer's actions populate it. Planned dates (needed_by, expected_on) may be today or later.
- private.reseed_if_stale(p_now timestamptz default now()): runs reset_demo's copy (private.apply_seed(private.ist_today())) only when private.reseed_due(p_now, demo_meta.anchor_date, latest idempotency created_at) is true: anchor_date < IST date of p_now AND no idempotency row in the 24 hours before p_now AND the IST hour of p_now is outside 08:00–22:00. Called only by public.reseed_if_stale_service(), which the scheduled job calls with the service key.
- Volumes (simulate real throughput): NCR ~32 bikes and JPR ~6–7 bikes per working day (Monday–Saturday; Sunday closed) over 90 days; opening balances (adjust_in, reason 'opening_balance') at anchor−180 for stocked parts. Keep the whole template under ~60,000 rows; if over, reduce findings per bike, not bikes per day.
- Simulated story: "before" period (days −90..−46): job cards confirmed only when the bike enters a bay, so more waiting and emergency buys. "After" period (days −45..−1): job cards confirmed at purchase, so parts are pre-reserved or pre-ordered. The metrics page shows the change, labelled simulated.
- Planted scenarios per workshop (assert minimums at reset): 3+ sent POs (one due tomorrow, one 2 days overdue, one partially received with damaged units); stock in receiving waiting for putaway (some of it reserved for a waiting bike); 3+ confirmed cards with fully reserved lines on bikes that are at_workshop or in_repair (ready to issue); blocked bikes with mixed causes (NCR 6+: PO in transit, overdue PO, not ordered, flagged fitment; JPR 4+: the same without flagged fitment); 3 independent demo chains (A, B, C): each is an in_repair bike blocked on exactly one part, with no other uncovered line for that part in the workshop, whose shortfall is exactly covered by its own sent, not-overdue PO (chain A's PO is the one due tomorrow). Receiving that PO takes the bike off the blocked board. Several reviewers can each walk a chain without a reset; 5+ auto parts at or below reorder point with no draft or open PO covering them (the simulator skips draft generation on the last simulated day so "Generate draft POs" has work to do); 8–12 dead-stock SKUs; 1–2 emergency buys in the last 7 days; 1 part with a flagged fitment (NCR only: fitments are shared master data, see seed catalogue 5.9); 1 unsourced part with a live shortfall; 1 bike with an unknown variant and an unresolved finding on a draft card. Planted codes are written to scripts/seed/planted.json; tests, README and the admin page read them from there and never hard-code them.

## §16 Deployment and operations
- Supabase in ap-south-1 (Mumbai). Vercel functions region bom1 (vercel.json "regions": ["bom1"]). Vercel env (Production): NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY (holds the publishable key, sb_publishable_…), NEXT_PUBLIC_DEMO_MODE=true, DEMO_PASSWORD (server-only; never NEXT_PUBLIC_). NEXT_PUBLIC_COMMIT_SHA is optional and set in next.config from VERCEL_GIT_COMMIT_SHA. Env is validated with Zod in two modules: src/env.client.ts parses an object that names each NEXT_PUBLIC_ variable literally (process.env.NEXT_PUBLIC_SUPABASE_URL etc.; Next.js inlines only literal references, so parsing process.env as a whole gives {} in the browser), and src/env.server.ts starts with import 'server-only' and parses DEMO_PASSWORD with the Zod schema from src/env.server-schema.ts (no 'server-only'; it exports only the schema, never values). next.config imports src/env.client.ts and parses process.env with the schema from src/env.server-schema.ts, so a bad value fails the build. next.config never imports src/env.server.ts: it runs in plain Node, where the 'server-only' package throws on import. Keys are trimmed non-empty strings (accept sb_publishable_/sb_secret_ and legacy eyJ… values); DEMO_PASSWORD is required when NEXT_PUBLIC_DEMO_MODE=true; the https-and-not-localhost URL rule applies only when process.env.VERCEL_ENV === 'production' (CI and local builds use http://127.0.0.1:54321). Vercel → Settings → Git → Ignored Build Step = "Only build production", so other branches never deploy against the production database.
- Migrations reach production only via `supabase db push`, run before every git push whose commit adds a migration (every push deploys). /api/health (dynamic, anon) calls public.health() which returns the latest applied migration version; the admin footer shows it with the commit SHA.
- GitHub Action "demo-guard" has two schedules plus a manual run. It reads the repo secrets SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY (the publishable key), SUPABASE_SERVICE_ROLE_KEY (the secret key), DEMO_PASSWORD and PROD_URL. Every 30 minutes ('*/30 * * * *' UTC): for each demo user, try signInWithPassword(DEMO_PASSWORD) with the publishable key and sign out with scope 'local'; only if that fails, call auth.admin.updateUserById(id, {password, email, email_confirm: true}), and fix the profile row only if it differs. Never update a password that still works: an admin password update logs out every session of that account. Every 6 hours ('0 */6 * * *' UTC): it calls public.reseed_if_stale_service() through supabase-js with the secret key (never curl with the secret key), and curls PROD_URL/api/health with --fail (keeps the free Supabase project from pausing and emails you if it fails).
- GitHub Action "ci" on push/PR, in this order: install, lint, typecheck, unit tests (TZ=America/Los_Angeles), pnpm seed:gen, supabase start (excluding services the app does not use), regenerate types and fail on diff, integration tests (no file parallelism), build, Playwright e2e against next start (its globalSetup re-applies the seed).
- Local seeding: supabase/config.toml [db.seed] sql_paths = ["./seed/template.sql", "./seed/apply.sql"]; apply.sql is `do $$ begin if to_regclass('demo_seed.meta') is not null then perform private.apply_seed(private.ist_today()); end if; end $$;`. After a fresh clone run pnpm seed:gen before supabase start. Every local `supabase db reset` wipes auth users, so run pnpm demo:users after it. Also fails if any existing file in supabase/migrations was modified, renamed or deleted.
